# よさこいアプリ 仕様・実装レビュー（2026年9月21日時点）

機能を「イベント → 道具 → お知らせ → イベント写真 → 過去イベントの非表示 → グループ/アンケート」の順につぎはぎで追加してきた結果、全体として一貫性があるか、抜け漏れがないかを通しで確認しました。db/schema.ts、lib配下の全ファイル、app/api配下の全APIルート、app/(app)配下の全ページとcomponents配下の全コンポーネントを読み直しています。

結論から言うと、**大きな設計崩壊はありません**。命名規則・フォーム送信方式（ネイティブform + Route Handler）・認可パターン（`requireAdmin`/`getCurrentMember`）・フラッシュメッセージの出し方などは、アンケート機能を含めて最後まで一貫して守られていました。ただし、実際に手を動かして初めて見える「積み上がった継ぎ足しゆえのズレ」がいくつか見つかったので、重要度順に報告します。

---

## 重要度：高（実際に動作がおかしくなりうるもの）

### 1. アンケートの対象者を後から変更すると、集計が壊れる

`src/lib/queries.ts` の `getSurveyResults()` は、`targetCount` と回答者名の表示を **「現在の対象者」** から逆引きしています。

```ts
const targetMembers = await getSurveyTargetMembers(surveyId); // 今の対象者のみ
const memberById = new Map(targetMembers.map((m) => [m.id, m]));
...
const member = response ? memberById.get(response.memberId) : undefined;
// → 現在は対象外になった人の回答は「不明なメンバー」と表示される
```

一方 `responseCount` は「これまでの全回答数」（`allResponses.length`）です。そのため、

- 回答後に対象グループを絞り込む（または対象者がグループから外れる／メンバーを無効化する）と、その人の回答は「不明なメンバー」として匿名化される
  → 記名式（誰が答えたか分かる）という要件と矛盾します
- 回答状況が「回答5/対象3」のように **分子が分母を超える** 表示になりうる
- 選択式の集計バーには、対象外になった人の回答も引き続きカウントされ続ける（表示上は矛盾するが数字自体は残る）

同根の問題はイベント機能側（`getEventWithResponses`）にもあります。無効化されたメンバーの過去の回答は `activeMembers` の一覧から漏れるため、`answered`/`unanswered` どちらのリストにも出てこなくなり、`getEventsWithCounts` の「未回答」件数（`activeMemberCount - counts.total`）がマイナスになり得ます。

**推奨対応**：表示用の「メンバー名の引き当て」は対象者フィルタと切り離し、`members` テーブルから ID で直接引く（無効化されていても名前は出す）。「対象者数」と「回答数」は、対象者を変更した後もどちらの意味の数字を見せたいか（現在の対象者内での回答率／これまでの総回答数）を決めて、UI上でも区別して表示するのが安全です。

### 2. `proxy.ts`（認可ミドルウェア）の対象パスに `/notices` と `/surveys` が抜けている

```ts
export const config = {
  matcher: ["/dashboard/:path*", "/events/:path*", "/tools/:path*", "/admin/:path*"],
};
```

`/notices` と `/surveys`（メンバー向けページ）がここに含まれていません。実際の未ログイン保護自体は `src/app/(app)/layout.tsx` の `getCurrentMember()` チェックで最終的にかかるため実害は今のところありませんが、このアプリの認可は「エッジのmiddlewareで一元的に弾く」設計のはずなのに、この2つだけ layout 側のフォールバックに依存する形になっています。

これは実はアンケート機能で新しく入った漏れではなく、**お知らせ機能を作った時点からあった漏れを、アンケート機能でも踏襲してしまった**ものです。まさに「つぎはぎ」の実例なので、今回まとめて直す価値があります。

**推奨対応**：`matcher` に `/notices/:path*` と `/surveys/:path*` を追加するだけの軽微な修正です。

### 3. 無効化(`isActive=false`)したメンバーの既存セッションが失効しない

`getCurrentMember()` はセッションのJWTからメンバーを引くだけで、`isActive` を見ていません。管理者が「メンバー管理」から誰かを無効化しても、そのメンバーがログイン済み（Cookieが最大30日間有効）であれば、無効化後もイベント回答・アンケート回答・道具状況の更新が引き続きできてしまいます（新規ログインだけはブロックされます）。

これはアンケート機能固有ではなく、アプリ全体に最初からある設計です。実害が出るのは「今すぐこの人の操作を止めたい」という場面（トラブル対応など）なので、優先度は中〜高くらいに見ておくのが良さそうです。

**推奨対応**：`getCurrentMember()` の中で `isActive` を確認し、`false` なら未ログイン扱い（`null`）で返すようにする。1関数の修正で全機能に波及するので費用対効果が高いです。

### 4. GET系のファイル配信ルートだけ、未ログイン時のリダイレクトが `resolveAppUrl` を通っていない

- `src/app/api/admin/events/[id]/export/route.ts`（CSV出力）
- `src/app/api/events/[id]/photos/[photoId]/route.ts`（写真取得, GET）
- `src/app/api/notices/attachments/[id]/route.ts`（添付ファイル取得）

の3箇所だけ `NextResponse.redirect(new URL("/login", request.url))` のように **素のrequest.url** を使っています。それ以外の全POSTルート（更新系）は一貫して `redirectWithMessage`（内部で `APP_URL` 環境変数を考慮する `resolveAppUrl` を使用）を経由しています。本番でリバースプロキシ配下など `request.url` と公開URLがズレる環境では、この3箇所だけログイン画面へのリダイレクト先がおかしくなる可能性があります。

**推奨対応**：この3箇所も `resolveAppUrl(request.nextUrl.origin)` を使うように揃える。

## 重要度：中（機能の一貫性・完成度）

### 5. ダッシュボードに「回答が必要なアンケート」がない

イベントには専用セクションがあり未回答件数が挨拶文にも出ますが、アンケートは下部ナビの「アンケート」タブに気づかないと存在にすら気づけません。これは前回の会話でも「あとで検討」として保留にした項目で、今回の通しレビューで正式に「抜け漏れ」と確定しました。イベントのセクションと同じパターン（未回答・受付中のものだけ抽出）で追加するのが自然です。

### 6. アンケート集計がN+1クエリになっている

`getSurveysWithCounts()` はアンケート件数分ループして `getSurveyTargetMembers()` を呼び、その中でさらに `member_groups` テーブルを毎回全件取得しています。イベント側の `getEventsWithCounts()` は全件を一度に取得してメモリ上で集計する効率的な実装になっており、アンケート機能だけこのパターンから外れています。数十人規模のチームでは体感差はほぼありませんが、「効率的な集計」という既存の設計方針からは外れています。

### 7. `getCurrentMember()` が1リクエストで最低2回呼ばれる

`layout.tsx` と各ページコンポーネントの両方で個別に呼んでおり、`members` テーブルへのSELECTが毎回2回発生します。これはアンケート機能に限らず既存の全ページに共通する問題です。React の `cache()` で `getCurrentMember` をラップするだけで、1リクエスト内の重複呼び出しが自動的にまとめられます（Next.jsのApp Routerで推奨されるパターンです）。小さい変更で全ページに効きます。

## 重要度：低（気づいたが実害はほぼないもの）

- `member_groups` テーブルだけ、似た役割の `member_tools` にある `updatedAt` を持っていません。実害はありませんが、カラム構成が微妙に不揃いです。
- `src/app/api/admin/members/[id]/route.ts` の管理者チェックだけ、他の全APIルートと書き方が違います（即時実行関数でtry/catchをラップ）。動作は同じですが唯一の例外です。
- アンケートは「質問内容を編集すると既存回答が全削除される」仕様（画面に警告表示済み）なのに対し、イベントは「内容を編集しても既存の回答はそのまま残る」仕様です。意図的な割り切りとして文書化済みではありますが、機能によって編集時の挙動が非対称なので、「これでよい」という認識合わせだけしておきたいところです。

---

## 良かった点（つぎはぎでも崩れていなかったところ）

- フォームは最後まで一貫してネイティブ `<form action method="POST">` + Route Handler。アンケートの動的質問ビルダーだけクライアント状態を持ちますが、hidden inputへのJSON埋め込みで送信自体はネイティブformのまま、という設計が保たれていました。
- 認可パターン（`requireAdmin`/`getCurrentMember`、フラッシュメッセージの付け方、`redirectWithMessage`）はほぼ全箇所で統一されていました。
- 「最初にログインした人が自動的に管理者になる」というオンボーディングの工夫は、招待の手間をなくす良い設計です。
- スキーマの命名・インデックス・カスケード削除の設計は、グループ／アンケートのテーブルも含めて一貫していました。
